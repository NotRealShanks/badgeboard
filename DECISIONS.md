# Architectural & Design Decisions

This document records the core architectural decisions, design choices, and trade-offs made in `badgeboard`.

---

## 1. Plain HTTP Over a Headless Browser
- **Context**: Profile pages on `skills.google` (and `cloudskillsboost.google`) are server-rendered HTML generated by a Rails application.
- **Decision**: Fetch HTML directly via standard `net/http` without running Chromium or a headless browser (Puppeteer, Playwright).
- **Rationale**: Server-rendered HTML renders completely in the initial GET response. Running a headless browser introduces significant memory overhead (hundreds of megabytes per instance), heavy binary dependencies, and 10x slower execution. Plain HTTP allows lightweight concurrent fetching with minimal resource footprint.

---

## 2. Structural Parsing vs Brittle CSS Selectors
- **Context**: The upstream markup uses transient styling classes (e.g. `.ql-title-medium`, `.l-mts`) that frequently change between frontend design releases.
- **Decision**: Anchor parsing on the structural link pattern (`/public_profiles/<uuid>/badges/<badge_id>`) and evaluate semantic relationships within badge card blocks rather than relying on presentation class names.
- **Rationale**: URLs represent stable domain entities in RESTful web applications. A change in stylesheet or CSS layout framework will not invalidate the parser as long as the resource URL structure remains intact.

---

## 3. Strict Distinction Between Zero Badges and Private/Inaccessible Profiles
- **Context**: When a participant's profile is private or unavailable (HTTP 404, redirect to sign-in), the page may contain no badges.
- **Decision**: Never report a private or inaccessible profile as `0 badges` (`StatusNoBadges`). A profile is only categorized as `StatusNoBadges` if positive confirmation of a public profile exists (valid `h1` display name plus secondary markers such as "Member since", avatar, or league/points block). Broken markup or server error pages return `StatusParseError`. Inaccessible or private profiles return `StatusPrivateOrNotFound`.
- **Rationale**: Misreporting private profiles as zero badges skews campaign metrics, unfairly penalizes participants, and distorts the completion funnel.

---

## 4. Profile Pagination & Verification
- **Context**: Real sample profiles from campaign organizers confirmed that active profiles render their earned badges in the primary `.profile-badges` block.
- **Decision**: Rather than silently returning a truncated badge count if an unhandled pagination control exists, the parser explicitly detects pagination controls (`.pagination`, `ql-pagination`, `[rel='next']`, or "load more" markers) scoped inside the badge container and immediately fails with `StatusParseError` stating:
  > `"profile pagination or 'load more' control detected in badge container; pagination parsing is unverified so aborting to avoid truncated badge count"`
- **Rationale**: Failing safe with `StatusParseError` prevents silent truncation and guarantees that incomplete data is never reported as authoritative progress.

---

## 5. Timezone & Date Normalization
- **Context**: Google Skills stamps badge completion dates in US Eastern Time (e.g., `Nov 3, 2026 EST`). Go's standard `time.Parse` with layout `MST` generates a synthetic zero-offset time zone if the three-letter abbreviation is not recognized locally.
- **Decision**: Explicitly parse calendar dates in `America/New_York` using embedded IANA timezone data (`_ "time/tzdata"`).
- **Rationale**: Guarantees deterministic calendar dates (year, month, day) regardless of the local timezone of the machine or CI runner executing the tool (whether running in UTC, Asia/Kolkata, or US Pacific).

---

## 6. Decoupling the Parser from Campaign Goals
- **Context**: The campaign goal defaults to 10 badges, but organizers may configure custom goals (e.g. `--goal 5`) or apply optional date windows.
- **Decision**: The HTML parser (`internal/parse`) extracts only raw facts (badges, display name, points, league). Status evaluation (`EvaluateStatus`) lives in `internal/model` and takes the configured goal. `ProfileResult` retains both `TotalBadges` (raw count) and `CountedBadges` (after campaign filters).
- **Rationale**: Clean separation of concerns. Changing the campaign goal or applying filters re-evaluates the model without re-parsing HTML or invalidating cached parse structures.

---

## 7. Global Cool-Down & Rate Limiting
- **Context**: When a server responds with HTTP 429 Too Many Requests or 503 with a `Retry-After` header, pausing only the failing thread risks other concurrent threads continuing to bombard the endpoint.
- **Decision**: When `Retry-After` is received, pause the shared limiter (`PauseUntil`) across all workers. Every retry attempt must re-acquire a rate limiter token.
- **Retry-After Clamp**: Capped at 60s by default (configurable). If the server demands more than 60s, `badgeboard` immediately aborts with `ErrRateLimited` rather than hanging indefinitely.

---

## 8. Cache Policy & Short Negative Cache
- **Context**: Failed network requests and unparsed pages should not pollute disk caches.
- **Decision**:
  - Cache only successful 200 responses (`StatusComplete`, `StatusInProgress`, `StatusNoBadges`) with standard TTL (6 hours).
  - Never cache transient failures (`StatusRateLimited`, `StatusNetworkError`, `StatusParseError`).
  - Cache `StatusPrivateOrNotFound` with a short separate negative TTL (15 minutes), so participants who make their profiles public can be refreshed quickly.
- **Atomic Writes**: Uses temporary files and atomic `os.Rename` to prevent file corruption.

---

## 9. Redirect & Payload Safety
- **Context**: Following arbitrary redirects or reading unbounded response streams exposes the engine to SSRF, open redirect abuse, or denial of service.
- **Decision**:
  - Redirects are capped at 5 hops and restricted strictly to authorized hosts (`skills.google`, `www.skills.google`, `cloudskillsboost.google`). Untrusted redirects return `ErrUntrustedRedirect`.
  - All response bodies are wrapped in `io.LimitReader` (2 MB). Bodies exceeding 2 MB return `ErrResponseTooLarge`.

---

## 10. Privacy & Anonymized Output
- **Context**: Roster files contain student names, emails, and profile URLs. Campaign dashboards are often deployed publicly via GitHub Pages.
- **Decision**: The CLI provides `--anonymize` for public output. Real roster files as well as `data/` artifacts are strictly gitignored.
- **Why Badge URLs are Dropped**: Upstream Google Skills badge links embed the full profile UUID (`/public_profiles/<uuid>/badges/<badge_id>`). Retaining badge URLs would enable anyone to extract the full UUID and reconstruct the participant's public profile URL.
- **Why Error Strings are Scrubbed**: Network timeouts, 404s, and rate limit messages frequently incorporate the target request URL, UUID, or student email into error text. These strings are systematically scrubbed via regex.
- **Why Bad Rows are Excluded**: Bad row diagnostics record raw input CSV lines (often containing pasted names, emails, or malformed URLs). In anonymized mode, the bad-rows collection is omitted from public exports to guarantee zero data leakage.

---

## 11. Formula Injection Neutralization in CSV Exports
- **Context**: Opening untrusted CSV exports in Microsoft Excel or Google Sheets presents formula injection risks (CSV injection / DDE attacks) if cells begin with execution triggers.
- **Decision**: Both the Go backend exporter (`internal/export`) and the client-side dashboard exporter (`docs/app.js`) automatically neutralize any cell starting with `=`, `+`, `-`, `@`, tab (`\t`), or carriage return (`\r`) by prefixing the cell with a single quote (`'`).

---

## 12. Two Data Tiers & Privacy Trade-offs (--anonymize vs --include-badges)
- **Context**: Even when direct identifiers (names, emails, profile URLs, UUIDs) are scrubbed, high-cardinality badge metadata (specific badge titles and completion dates) can act as quasi-identifiers. In small cohorts, a unique combination of earned badges could theoretically correlate back to an individual's public profile.
- **Decision**: `badgeboard` implements a tiered data privacy model:
  1. **Tier 1: Public Mode (`--anonymize`, default for public dashboard)**:
     - Exports only minimal progress data per student: pseudonym, status, counted badges, total badges, goal, and last badge date (`YYYY-MM-DD` date only).
     - Strictly omits: badge lists, badge titles, per-badge dates, badge URLs, league, points, profile URLs, UUIDs, and full-precision timestamps.
     - Protects against quasi-identifier linkage and correlation attacks.
  2. **Tier 2: Detailed Anonymized Mode (`--anonymize --include-badges`)**:
     - Retains badge titles and dates for expandable detail views while continuing to scrub direct names, emails, profile URLs, UUIDs, and badge URLs.
     - **Trade-off**: Requires an explicit opt-in (`--include-badges`) because publishing full badge catalogs introduces minor re-identification risk in very small groups.
  3. **Tier 3: Full Mode (Default CLI / Demo / Internal)**:
     - Full profile details (display names, leagues, points, badges, URLs) for internal administrative use and demo dashboard testing.

---

## 13. Irreversible Pseudonym Derivation via Secret-Salted HMAC-SHA256
- **Context**: Reversible pseudonyms or naive truncation (such as `"A. J. (ddd7)"`) leak quasi-identifiers: learner initials combined with the last 4 characters of the raw UUID permit an adversary with access to a public Google Skills directory or social shares to easily deanonymize participants.
- **Decision**: `badgeboard` generates pseudonyms strictly in the format `Learner-XXXX` using `HMAC-SHA256` keyed with an out-of-band secret salt:
  $$\text{HMAC-SHA256}_{K}(\text{lowercase(UUID)})$$
  The first two bytes (16 bits) are truncated to four uppercase hexadecimal characters.
- **Enforcement**:
  - The CLI refuses to execute `--anonymize` unless a secret salt is supplied via the `BADGEBOARD_SALT` environment variable or `--salt-file <path>`.
  - For testing and reproducible demo builds, `--demo-salt` must be explicitly passed.
  - The salt is strictly kept out of version control and git history.
  - Different salts produce entirely non-overlapping pseudonyms for the same input UUID, preventing correlation across cohorts or events.

---

## 14. Public Deployment Policy & Real Roster Governance
- **Decision**: The public GitHub Pages site deployed from `docs/` serves synthetic demo data generated via `badgeboard demo` exclusively.
- **Mandatory Privacy Invariant**: Real participant data must never be published without the organizers' explicit permission.
- **Guarded Workflows**:
  - Any CI/CD workflow capable of reading and processing real participant rosters must remain **disabled by default**, restricted to manual `workflow_dispatch`, and guarded by repository variables (`ENABLE_REAL_ROSTER == 'true'`) and encrypted repository secrets (`REAL_ROSTER_CSV`, `BADGEBOARD_SALT`).

---

## 15. Why Go?
- **Decision**: Implemented in Go 1.22+.
- **Rationale**:
  - Single static binary distribution without runtime dependencies (Python, Node, Docker).
  - First-class concurrency (`sync`, channels, worker pools) for high-performance polite scraping.
  - Robust standard library for networking, testing, and HTTP mocking (`httptest`).
